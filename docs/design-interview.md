## 實作設計參考

以下是官方語意與設計推論，並非本專案已通過測試或量測的證據。

- PostgreSQL 的條件式更新與列鎖需配合一致的交易邊界；跨列的購票額度不能只靠單一座位更新保護。[交易隔離](https://www.postgresql.org/docs/16/transaction-iso.html)、[列鎖](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS)。
- `now()` 固定於交易起點，`statement_timestamp()` 固定於指令起點；會等待鎖的付款流程須取得相關鎖後再以 `clock_timestamp()` 判斷截止時間。[時間函式](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)。
- Sequence 可能跳號，且取號順序不代表交易提交順序。事件漏失偵測需另設與狀態一起提交的活動版本。[Sequence](https://www.postgresql.org/docs/16/functions-sequence.html)。
- Redis Pub/Sub 為 at-most-once，不能補送漏掉的訊息；即使最後一筆通知漏掉、後面沒有新事件，也須能以版本校驗發現。[Pub/Sub](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics)。
- 跨 HTTP 請求各自開啟交易，無法自然維持同一資料快照；exported snapshot 仍受原交易生命週期限制，因此固定清單規劃使用有期限的物化結果。[快照同步](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION)。
- OpenPyXL write-only 的記憶體特性不等於整個報表 API 已符合 512MB。查詢批次大小、暫存檔與回傳方式仍須設計並實測。[Optimised Modes](https://openpyxl.readthedocs.io/en/stable/optimized.html#write-only-mode)。
